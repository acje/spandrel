1. Demarcation of Ownership

gh-report (Application Layer)

  • Domain business rules, commands, and aggregate invariants
  • Compiled monotonic merge and status anti-downgrade logic
  • Presentation view models and HTML rendering (Askama)
  • Application routes, authentication, and external API observation

Spandrel (Substrate Layer)

  • Domain traits, envelopes, and read-only query ports (ReadPort)
  • Bounded work queues, execution runners, and pacing regulators
  • Decoupled projection fold accumulators and stream schedulers
  • Synchronous storage durability utilities and advisory file locks
  • Standard HTTP serving pipeline (Axum, ETag/304, zstd, WebSocket)
  • Zero Cargo dependencies on Pardosa in core crates

Pardosa (Stream Substrate Layer)

  • Physical append-only commit line (.pgno container format)
  • Total commit ordering and per-fiber linearizability
  • Single-writer CAS ownership fencing
  • Causal precursor commit chains and BLAKE3 frame integrity

2. Change-Driven Capability Pipeline

1 Ingest & Validate gh-report

Webhook signature validation and task enqueue. Acceptance != completion != commit.

2 Dispatch & Pace Spandrel

Bounded work queue dispatches to worker pool under pacing regulators (budget gate / token bucket).

3 Decide & Propose gh-report

Worker executes command logic (decide(cmd, state) -> Events); aggregates bound consistency where required.

4 Commit & Reconcile Pardosa

Events commit via synchronous stream append above CAS fencing. Undetermined outcomes require probe reconciliation.

5 Stream Feed (Live/Replay) Spandrel

Confirmed committed events stream incrementally to live folds or sequentially from store start during replay.

6 SAME Projection Fold Spandrel

Live and historical events fold deterministically through the exact same logic (apply(&mut self, payload)).

7 Render & Publish gh-report

Changes trigger view rendering; outputs are zstd-compressed, ETag-hashed, and published to html_cache via ArcSwap.

8 Standard HTTP Serve Spandrel

Serves cached pages directly (returning 304 on ETag match) and emits WebSocket live updates only on change.

3. Component Coverage (8 Donor Crates)

Donor Crate Target Component Scope & Included Utilities
cherry-pit-core Domain & Read Ports Domain traits (DomainEvent, Command, HandleCommand, Aggregate, Policy), envelopes/IDs (AggregateId, IdempotencyKey), and read-only ReadPort. Testing fakes/clocks.
cherry-pit-storage Storage & Durability Synchronous file durability (atomic_write_bytes via fsync), advisory RunLock with TTL, snapshot hashing, and persistence error models.
cherry-pit-gateway Recovery Utilities Stale lock recovery helpers belong with storage utilities; no separate gateway crate required.
cherry-pit-merger Command Serialization Optional local actor (Merger) serializing command submissions. Local serialization alone grants no stream append authority or transaction guarantee.
cherry-pit-projection Read-Side Projections Decoupled payload-first Projection fold and checkpoint tracking. Core maintains zero direct Cargo dependencies on Pardosa.
cherry-pit-web HTTP Serving & Publication Axum serving pipeline (serve), path normalization, security headers, ETag/304 negotiation, zstd compression, and WebSocket updates.
cherry-pit-wq Concurrency & Pacing Bounded work queue with pending dedup, regulated worker pool, batch tracking, backoff/retry/settle policies, and rate limit pacers.
cherry-pit-app Scheduling, Bus & Utilities Generic scheduler with arm/cancel/due/recovery hooks (durability depends on caller store), in-process bus, and dead-letter sink.

4. Reliability & Resource Semantics

Reconciliation

An append error does not prove commit failure. Callers must reconcile undetermined outcomes against the stream before retrying or failing.

Cursor Scope

Dragline cursors have stream-local validity and are invalidated across migrations; durable external cursors are not guaranteed.

Resource Contracts

Explicit bounds on queued items and owned heap capacity (payloads/buffers); backpressure, deadlines, and bounded shutdown are required.

5. Minimal Pilot Focus

The first implementation target will validate the decoupled payload-first Projection fold inside the existing gh-report runtime under a single-process local-file assumption, retaining the existing queue, workers, store, and server while validating commit-before-fold gap recovery, duplicate refresh semantics, and rendered-state equivalence against live stream catch-up.
